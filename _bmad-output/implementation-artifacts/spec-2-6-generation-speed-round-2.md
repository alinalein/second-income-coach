## Intent

**Problem:** After round 1 (`spec-2-4-2-6-faster-generation-more-ideas.md`), a live run still measured 100-155s for a 2-idea batch (vs a 35-60s baseline). Round 1's own Implementation Notes already found the cause for one live run: two whole-batch attempts rejected on the same hard check, then an accepted repair pass — three serial full nested-agent round trips.

**Approach:** First log, per attempt, elapsed time and the rejection reason, and whether/how long the repair pass ran, under `WEB_SEARCH_MODE=stub` (no live-run yet) — report honestly before changing anything. Then restructure `generate_ideas.ts` so each idea of the batch is generated by its own independent nested-agent call, run in parallel (`Promise.all`), each with its own up-to-`MAX_DRAFT_ATTEMPTS` retries scoped to that one idea only — so a failing idea retries alone without redoing a sibling that already succeeded, and wall time tracks one idea's call instead of the whole batch's. Cross-idea soft rules (idea-type variety, citation-domain spread/cap) are computed once after all ideas are combined, exactly as today (log-only, never blocking). Every hard rule (`evaluateDraft`) stays unchanged and still applies per idea before that idea is accepted.

## Boundaries & Constraints

**Always:** every hard check in `evaluateDraft` stays exactly as strict, applied per idea; `web_search` call count per nested-agent invocation and moderation coverage stay unchanged (2.11's cap/cache middleware is untouched); `DRAFT_ATTEMPT_TIMEOUT_MS` and `MAX_DRAFT_ATTEMPTS` are not raised; all N ideas still insert in one DB transaction — a run where any one idea never produces a hard-valid draft within its own attempt budget still persists zero rows (Boundary carried over from round 1); `SearchServiceUnavailableError` (every web_search call in one nested-agent invocation failed) still aborts the whole run immediately with no DB write, whichever idea's call hits it first.

**Never:** weaken quote verification, moderation, vendor/login-wall rejection, or any occupation/currency/budget check; reduce searches per idea below what 2.2/2.5 already require (>=1 baseline + >=1 demand-evidence); add a new retry layer on top of the existing per-idea `MAX_DRAFT_ATTEMPTS` budget; touch `web-search-budget-guard.ts`, `create_plan.ts`, `IdeasPanel.tsx`, or translation — out of scope for this round.

## Implementation Notes

**Diagnosis (before, 3x `WEB_SEARCH_MODE=stub`, real OpenRouter model calls, IDEAS_PER_BATCH=2):**
- Run 1: 36.8s, 1 whole-batch attempt accepted (5 sequential model calls inside one nested-agent invocation).
- Run 2: **failed after 83.9s** — attempt 1's final model call ran 51.7s and produced no structured output at all (`result.structuredResponse` undefined); attempt 2 (27.1s) produced 2 drafts that **both** failed the same hard check (`quoteCurrencyMismatch`) — zero valid slots, so the repair pass's own precondition (`validIndexes.length > 0`) never fires, and the whole batch is discarded with no DB write.
- Run 3: 39.8s, 1 whole-batch attempt accepted.
- Repair pass never ran in any of the 3 runs (`ran: false` every time) — confirms round 1's own live finding (153.2s: 2 rejected attempts + 1 accepted repair) and this round's regression share one root cause: every retry — the normal attempt-2 *and* the repair pass — redoes/depends on the full multi-idea batch's own model+search round trip; nothing was scoped to the one idea that actually failed until repair, and repair itself needs at least one valid sibling to anchor on.

**Fix:** restructured `handleGenerateIdeas` into N independent per-idea slots (`generateOneIdeaSlot`), each with its own up-to-`MAX_DRAFT_ATTEMPTS` loop calling `generateDrafts(..., { count: 1, ... })`, run via `Promise.all`. Removed the whole-batch repair-pass block (redundant — a slot's own 2nd attempt already does what repair used to do, scoped to just that idea). Cross-idea soft rules (idea-type variety, citation-domain spread/cap) are computed once after all slots resolve, by re-running the existing `evaluateBatch` over the merged drafts + merged search texts (safe/idempotent — a hard check only gets easier to satisfy with more search results, never harder).

**Re-diagnosis (after, first pass, 3x stub, before the prompt-wording fix below):** 84.5s / 83.4s / 92.2s — all 3 succeeded (vs. before's 1 outright failure), but slower than hoped. A targeted deeper run showed why: one slot's first attempt ran 49.4s and hit `NESTED_AGENT_RECURSION_LIMIT` (13) without producing output, then succeeded in 23.3s on its retry, while the sibling slot (independent, in parallel) had already succeeded in 48.3s — `Promise.all` waits for the slowest slot, so one stalled slot dominates the whole run's wall time. Traced one plausible contributor to `buildNestedAgentPrompt`'s cross-idea diversity wording becoming self-contradictory at `count === 1` (e.g. "no single domain as the source for more than 2 of the 1 ideas," "distinct idea types across the 1") — fixed by dropping that wording entirely when `count === 1` (cross-idea variety is checked afterward by `evaluateBatch` regardless, so a single-idea call has nothing useful to say about batch-wide diversity).

**Re-diagnosis (after, final, 3x stub):** 72.8s / 43.3s / 34.7s → re-ran after the prompt fix: still one run at 72.8s (slot 0 again hit the recursion limit on its first attempt, 49.4s, before succeeding on retry in 23.3s) — the prompt fix did not eliminate the recursion-limit stall itself, only the self-contradictory wording that was one plausible contributor. **Honest miss:** 1 of 3 post-fix runs (72.8s) exceeds the "never above ~60s" target. Root cause is `NESTED_AGENT_RECURSION_LIMIT` (13) occasionally not being enough for a single nested-agent invocation to converge — this is pre-existing agent-loop variance (documented in the codebase as "a generous-but-bounded ceiling, not a tuned value"), not a hard-rule rejection or a cause this round's Boundaries permit fixing (raising the limit works against the speed goal and isn't a timeout per se, but isn't a reliable fix either — it lets a stalled call run *longer*, not resolve faster). The other 2 of 3 runs (43.3s, 34.7s) meet target. Net effect vs. before: the single-point-of-total-failure mode (0 ideas after 84s) is eliminated — every post-fix run eventually succeeds — at the cost of occasionally hitting a slower tail when one of the now-independent per-idea calls stalls on the pre-existing recursion limit.

**Quality checks confirmed unchanged:** every hard check in `evaluateDraft` (quote verification, vendor/login-wall rejection, occupation/currency/budget limits) runs per idea exactly as before; `evaluateBatch`'s soft checks (Story 2.2/2.5: idea-type variety, citation-domain spread/cap, demand-evidence domain spread/cap) still compute and log, never block; `web_search` call count per invocation, moderation coverage, `DRAFT_ATTEMPT_TIMEOUT_MS`, and `MAX_DRAFT_ATTEMPTS` are all unchanged.

Full suite verified independently after implementation: shared 37/37, src 362/362, web 79/79 passed; `npm run typecheck` clean across all three workspaces.

## Design Notes

The whole-batch repair pass (round-1-era: one extra call asking only for the slots that failed hard checks, merged with the kept-good slots) becomes structurally redundant once every idea already gets its own independent attempt loop — a per-idea "2nd attempt" already *is* "ask again for just this one idea, excluding titles," which is exactly what repair used to do at the whole-batch level. Removing the separate repair-pass code path is a simplification, not a new retry layer: the total retry budget per idea stays exactly `MAX_DRAFT_ATTEMPTS` (2), unchanged from round 1.

`web-search-budget-guard.ts`'s per-run search cap (`MAX_SEARCHES_PER_RUN`, default 6) is scoped to one nested-agent invocation's own middleware instance today (pre-existing characteristic, not introduced by this round) — it was never a strict cross-attempt/cross-idea ceiling even before this change (round 1's 2 full-batch attempts + 1 repair call could already exceed 6 real searches in aggregate). This round's per-idea parallel calls change the aggregate worst case from "up to 3 invocations x 6" to "up to 2N invocations x 6," which is a pre-existing characteristic scaling with idea count, not a new gap this round introduces or is asked to fix.
