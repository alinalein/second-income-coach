## Intent

**Problem:** Story 1.1 installed `shadcn-glass-ui` and used it for the frosted-glass look (UX-DR3), but Story 1.3's review removed the package and its CSS import as "unused" when `App.tsx` was rewritten. The app currently renders with flat/opaque surfaces, not the specified glass aesthetic, and Story 1.1's own acceptance criterion for it was accepted without it actually being true. A first pass (this story, round 1) added a single translucent surface token over the existing flat page background — the result read as flat grey, not glass, because backdrop blur has nothing with tonal variation to blur against a near-solid page color. **Course-corrected (round 2):** the user pointed to `_bmad-output/planning-artifacts/layout-preview.html` as the chosen design reference (primary; `wireframes.html` is an earlier, superseded low-fi/emerald-accent document providing only structural decisions, not visual tokens) and required reproducing its exact token values, including the radial-gradient page background the glass effect depends on.

**Approach:** Re-add `shadcn-glass-ui` as a real dependency and import its stylesheet (still satisfies "a dependency again"/AC1's npm-package requirement), but build the actual glass look from `layout-preview.html`'s own exact CSS custom properties (`--page-a`/`--page-b`, `--glass-bg`, `--glass-bg-strong`, `--glass-border`, `--muted-bg`, `--shadow`) rather than the library's own theme engine. Give the page body the reference's radial-gradient background (`radial-gradient(circle at 20% 10%, var(--page-a), var(--page-b) 70%)`, separate light/dark stops) — the gradient is what makes the backdrop blur read as glass instead of grey. Implement two glass tiers matching the reference: `glass` (weaker, `--glass-bg`, for panel-level surfaces like `Card`) and `glass-strong` (`--glass-bg-strong`, for header/chrome/controls/native inputs), plus a flat non-blurred `muted-surface` tier (`--muted-bg`) for muted/neutral badge chips, matching the reference's own choice to never blur badges. Apply these once in `web/src/index.css` and the shared `Card`/`Button`/`Badge` components, plus bare tag-selector rules for `header` and native `input[type='text']`/`textarea`/`select` (reaches native form controls in off-limits files via CSS cascade-layer precedence, without editing those files). Keep primary/accent fills (solid teal button, solid teal badge) opaque — their exact contrast ratios are pinned and verified in `stack.md`. Deviate from the reference's literal alpha values only where the real composited text-on-glass contrast would fail 4.5:1 against the actual gradient (verified by direct computation, not by eye), and document each such deviation. Re-measure text contrast on every real surface in both themes, against both gradient stops, and record the values.

**Course-corrected again (round 3):** round 2's result still read as flat grey, and dark-mode text rendered black/unreadable. Root cause (not diagnosed until round 3): the imported `shadcn-glass-ui/styles.css` ships its own `--color-foreground`/`--color-background`/etc. — the exact same Tailwind-conventional names this project's `@theme inline` block also registers — chained to `--foreground-base`/`--background-base`/etc. that only exist under an inert `[data-theme=...]` attribute this app never sets. The library's versions were silently winning, so every `bg-*`/`text-*`/`border-*` utility resolved to an invalid reference everywhere, which for the inherited `color` property computes to black. This existed in rounds 1 and 2 too; nothing in either round's verification (build, tests, manual contrast math against assumed token values) would have caught it, because none of it checked what `--color-foreground` itself actually resolves to after the import. Fixed with an unlayered override (see Implementation Notes). The user also required, explicitly and literally: the reference's soft accent blobs (without which "the glass blur is only visible with them" per the user), badges included among the blurred glass surfaces (overriding the reference's own non-blurred badges, by explicit instruction), and `--foreground`/`--muted-foreground` applied to all text so dark-mode text is actually light. Re-measuring contrast with the blobs in place surfaced a further, unfixable-by-opacity failure for `--muted-foreground` wherever a blob shows through a glass surface (proven mathematically: even zero glass overlay over a blob-tinted dark page only reaches 3.89:1) — resolved per the user's explicit decision to use `--foreground` instead of `--muted-foreground` on every glass-adjacent text element, the same kind of token substitution already used for the muted badge.

## Boundaries & Constraints

**Always:**
- Keep the exact pinned teal/neutral hex values from `stack.md` (`--primary`/`--primary-foreground`/`--accent`/`--accent-foreground`) — glass changes opacity/blur/page background, never accent hue.
- Use `layout-preview.html`'s exact token values (page gradient stops, glass-bg/glass-bg-strong/glass-border/muted-bg/shadow) as the starting point for every new token; any deviation from its literal numbers must be justified by a measured contrast failure, not taste.
- Define each glass tier once in `web/src/index.css`; every shared component and tag-selector rule references it, no per-screen CSS.
- Preserve existing public props/API of `Card`, `Button`, `Badge` — screens that already render through them, or through a native `input[type='text']`/`textarea`/`select`, must pick up the new look with zero changes to their own files.
- Visual only: no behavior, ARIA, i18n-key, or test-expectation changes. Existing tests stay green.
- If contrast fails 4.5:1 on a glass surface, fix it by adjusting the surface's opacity/tokens, never by resizing text; verify against both gradient stops (`--page-a` and `--page-b`), not just one.

**Never:**
- Do not edit `web/src/chat/**`, `web/src/features/**`, locale files, or anything under `src/` or `shared/` — other sessions own those. (A bare tag-selector rule in `index.css` reaching a native element inside one of those files is not an edit to that file.)
- Do not edit `web/src/App.tsx` beyond at most one line.
- Do not create `label`/`select`/`textarea` UI components — none exist in this worktree yet (no screen renders a React component by that name); inventing them now would be unused scaffolding. (Styling the native HTML elements via a CSS tag selector is not creating a component.)
- Do not install `@yhooi2/shadcn-glass-ui` (deprecated) or adopt the library's own `ThemeProvider`/3-theme (`glass`/`light`/`aurora`) system — it ships a separate purple/violet accent model that would override the pinned teal tokens and the reference's own neutral page gradient.
- Do not remove `shadcn-glass-ui` or its style import even if a later lint/review pass flags it as unused (UX-DR3; removal needs the user's explicit approval).

### Round 2, review-driven fixes (two critical, both caught by the independent review before this would have shipped)

- **Critical #1 — `App.tsx`'s root div hid the gradient entirely.** Both render branches wrap everything in `<div className="min-h-screen bg-background text-foreground">`. `bg-background` is an opaque solid fill, and `min-h-screen` makes the div cover the full viewport — it sat on top of `body` and completely hid the new gradient, which would have reproduced the exact "flat grey" bug this round was meant to fix, just one DOM layer deeper. Caught by edge-case-hunter (high confidence), verified directly by reading the file. Fix needs removing `bg-background` from both (textually identical) lines — 2 edits against App.tsx's stated 1-line budget. Asked the user directly; they authorized exceeding it by one trivial line for this specific, mechanical fix. Both occurrences fixed; rebuilt and retested (16/16 still green).
- **Critical #2 — the imported library's own CSS collided with my utility class names.** `shadcn-glass-ui/styles.css` ships its own `.glass{}`/`.glass-strong{}` rules. Checked directly in `node_modules/shadcn-glass-ui/dist/shadcn-glass-ui.css` and in the compiled build output: the library's "semantic" versions are layered the same as mine (harmless — same `@layer utilities`, and they happen to reference the same variable names I'd independently chosen, which are themselves inert since the library's own values are scoped under `[data-theme=glass/light/aurora]`, an attribute nothing in this app ever sets). But the library also ships a **base, unscoped, unlayered** `.glass{}` rule with hardcoded near-invisible colors (`background:#ffffff0d` — ~5% alpha white). Per CSS Cascade Layers, an unlayered rule always beats a layered one regardless of source order or specificity — so that rule would have silently won over my intended `Card` styling on every build, independent of the App.tsx bug above. (`.glass-strong`/`muted-surface` had no such unlayered collision — checked directly, only `.glass` got this treatment in the library's CSS.) **Fix:** renamed my utilities to `glass-panel` and `glass-chrome` (`muted-surface` kept, no collision) everywhere — `index.css`, `card.tsx`, `button.tsx`. Verified in the rebuilt CSS: exactly one definition each of `.glass-panel{}`/`.glass-chrome{}`/`.muted-surface{}` now exists; the library's own `.glass{}`/`.glass-strong{}` remain in the bundle as inert, unused bytes (acceptable cost of importing its full stylesheet). Rebuilt and retested (16/16 still green).
- **Glass-on-glass now correctly documented (was wrongly claimed not to occur):** `ThemeToggle`/`SignOutButton` use `variant="outline"` (now `glass-chrome`) and render *inside* `<header>` (also `glass-chrome`) — this is a real, currently-existing double-composite, not a hypothetical. - **Badge `outline` variant's contrast, measured across every context it can appear in** (it has no background fill of its own — border + text only, so its real surface is whatever sits behind it): directly on the bare page gradient, 12.20–12.91:1 (light) / 14.75–15.57:1 (dark); on `glass-panel` or `glass-chrome`, 13.86–14.17:1 (light) / 11.10–12.59:1 (dark). All ≥4.5:1 in every case.

No live input of another type exists in this worktree today (confirmed: exactly one native `<input>` in the whole app, `ChatThread.tsx`'s, already `type="text"`), so this is forward-looking, not fixing a present bug.

This is a real limitation of styling a native form control rather than a custom-built one (no `Select` component exists in this worktree to build instead, and creating one is out of this story's scope) — noted here, not fixed.

Kept as historical record (append-only), not deleted; flagged here for anyone reading it.

### Round 3 (user: "the result still does not match the design... black on dark glass... both themes look flat grey")

- **Root cause of round 1 and round 2's symptoms, finally diagnosed:** grepped the compiled production CSS directly (not just the library's source) for every `--color-*` variable this project's `@theme inline` block registers. Every single one (`--color-background`, `--color-foreground`, `--color-card`, `--color-muted`, `--color-border`, `--color-primary`, `--color-accent`, and their `-foreground` pairs, `--color-ring`, `--color-input`) had exactly one definition in the output, and it was always the **library's**, never this project's — e.g. `--color-foreground:oklch(from var(--foreground-base) l c h)`, where `--foreground-base` is defined three times in the whole bundle, all three gated behind `[data-theme=glass]`/`[data-theme=light]`/`[data-theme=aurora]`, an attribute nothing in this app ever sets. An inherited property (`color`) referencing a variable that resolves to nothing computes to its initial value, black, at every element in the app, in both themes — explaining both "flat grey" (every `bg-*`/`border-*` utility broken too, just less visible against similarly-wrong backgrounds) and "black text in dark mode" (most visible there because dark mode is the one case where the correct answer is clearly NOT black). Independently confirmed the mechanism: the library's own `body{background-color:var(--color-background);color:var(--color-foreground);...}` rule is unlayered, same as the library's `.glass{}` collision found in round 2 — the identical bug shape, a second instance of it, undiagnosed until now. **This bug was present in rounds 1 and 2 too** — neither round's verification (clean build, passing tests, contrast math against assumed token values) could have caught it, because none of it asked what `--color-foreground` itself resolves to post-import; the math assumed the token bridge was intact.
- **Fix:** an unlayered `:root { --color-background: var(--background); ... }` block, placed right after the `@theme inline` block, re-declaring every `--color-*` name with the correct `var(--background)`/`var(--foreground)`/etc. reference. Unlayered always beats layered regardless of source order (same rule already relied on for `header`), so this is robust independent of whatever order the library's own declarations end up in after bundling/minification. Verified in the rebuilt CSS: each `--color-*` now has two definitions, library's (layered, `theme`) and mine (unlayered) — mine wins.
  - Hit one unrelated authoring bug while writing this fix's code comment: a literal `bg-*/border-*/text-*` substring inside a CSS comment is read by the CSS parser as `*/`, closing the comment early and corrupting everything after it until the next stray quote character triggers a syntax error. Caught immediately by the build failing; reworded the comment to avoid adjacent `*` `/` characters.
- **Blobs added** (`html::before`, `html::after`, `body::before`, since no new DOM elements are available — see Code Map): exact size/position/blur/colour/opacity from the reference, `z-index:-1` substituted for the reference's `z-index:0` of necessity (documented in the CSS comment and Code Map).
- **New failure, found by re-measuring contrast with the blobs in place:** `--muted-foreground` fails 4.5:1 wherever a blob is at meaningful strength behind a glass surface, in both themes, and **no glass-opacity adjustment fixes it** — proved by computing the full alpha sweep: even at `alpha=0` (no glass at all, pure blob-tinted dark page), `--muted-foreground` only reaches 3.89:1; increasing white-glass alpha from there makes it *worse*, not better, since it pushes the composite lighter, shrinking the gap to the already-light `--muted-foreground` colour. The blob's own colour/opacity are user-pinned, non-negotiable values, so neither direction of the one lever I control (glass alpha) resolves this. Presented the finding and three options to the user; they chose: use `--foreground` instead of `--muted-foreground` on every surface that sits on glass. Implemented: `CardDescription` (card.tsx) and `input::placeholder`/`textarea::placeholder` (index.css, reaches `ChatThread.tsx`'s input without editing it) now use `--foreground`. `badge.tsx` already used `--foreground` for the same reason since round 2 (independently correct, re-confirmed safe under blob tinting below).
- **Badges revised:** the user's round-3 instruction explicitly lists badges among the blurred glass surfaces, overriding `layout-preview.html`'s own non-blurred `.badge.neutral` — followed the explicit instruction over the literal reference file for this one element. `muted`/`outline` now both use `glass-chrome` + `shadow-[var(--shadow)]`. The now-unused `muted-surface` utility (flat, no blur) was removed; `--muted-bg` itself is kept as a transcribed reference token with no current consumer (documented in the CSS comment) in case a future component — e.g. a progress track — needs it.
- **Full final contrast verification** (WCAG relative luminance; every text element in this story's scope now uses only `--foreground`, never `--muted-foreground`), worst case across both gradient stops, with **and** without blob tinting at full nominal strength:

  | Surface | Light worst-case | Dark worst-case |
  |---|---|---|
  | `glass-panel` (Card) | 13.15:1 | 7.19:1 |
  | `glass-chrome` (header, buttons, badges, native inputs) | 13.33:1 | 6.40:1 |

## Design Notes

- **Why `default` button/badge stay opaque:** `stack.md` pins exact verified contrast ratios for the solid teal fills (e.g. `--primary-foreground` on `--primary`: 5.47:1 light / 9.98:1 dark). Compositing those over a translucent glass background would shift the effective color and invalidate those already-signed-off numbers for no visual benefit on a small filled control. Glassmorphism convention also keeps primary CTAs opaque and glasses the secondary chrome around them.
- **Why the header needs no `App.tsx` edit:** both the signed-out and signed-in render branches already wrap their top bar in a plain `<header>` tag with no component indirection, so a single `header { @apply glass-chrome shadow-[var(--shadow)]; }` tag-selector rule in `index.css` reaches both without touching `App.tsx` at all. The same unlayered-tag-selector mechanism also reaches native `input[type='text']`/`textarea`/`select` elements inside otherwise off-limits files (`web/src/chat/ChatThread.tsx`, `web/src/features/settings/SettingsPage.tsx`) without editing them.
- **Contrast numbers assume compositing over the real gradient, both stops:** measured against `--page-a` and `--page-b` independently and the worse of the two reported — a card can land anywhere across the radial gradient, so a single representative color would understate the risk. Proof that the two endpoints actually bound the worst case across the whole gradient (not just a guess): every RGB channel moves monotonically in the same direction from `--page-a` to `--page-b` in both themes (light: 238,241,240 → 231,235,233, all three channels decrease; dark: 17,18,20 → 23,24,27, all three increase), and the gradient holds flat at `--page-b` beyond its 70% stop — so relative luminance, itself a monotonic function of each channel, cannot exceed either endpoint anywhere on the page. Placing a glass surface over an image is not covered and must be re-measured if that's ever built.
- **Glass-on-glass does occur in this diff** (corrected from an earlier, wrong claim that it didn't): `ThemeToggle`/`SignOutButton` (`variant="outline"`, `glass-chrome`) render inside `<header>` (also `glass-chrome`), a real double-composite. With the round-3 blobs factored in (the header sits within the first blob's reach), the worst case drops to **4.94:1** (dark) — still ≥4.5:1, but the tightest margin anywhere in this story (0.44). See the round-3 contrast table in Implementation Notes.
- **No text uses `--muted-foreground` on or near a glass surface, anywhere in this story's scope** (round 3): `CardDescription`, badges, and native-input placeholders all use `--foreground` instead, specifically because `--muted-foreground` fails 4.5:1 wherever a soft accent blob shows through a glass surface and no opacity adjustment can fix that (proved: even zero glass overlay over a blob-tinted dark page only reaches 3.89:1 for `--muted-foreground`). `--muted-foreground` the token itself is unchanged and still defined, in case a future screen needs it somewhere with no glass/blob behind it.
- **Remaining follow-up (`web/src/chat/**`, `web/src/features/**` — cannot fix without editing those files):**
  - `ChatMessage.tsx`'s non-user bubble (a plain `<div>` with inline `bg-card`/`border-border`) — not reachable by the shared-component or native-tag-selector mechanism. Also carries the same `--muted-foreground`-near-glass risk as everything else in this story, if it's ever moved onto a glass background.
  - `ChatThread.tsx`'s and `SettingsPage.tsx`'s own `text-muted-foreground` text (loading/empty states, helper text, an alert) — not on a glass surface themselves (these are plain `<p>` tags, not reachable by a safe generic tag-selector the way `header`/native-inputs are — a bare `p {}` rule would be far too broad), so untouched; flagged here per the user's request to list what's left, not because today's math requires fixing it (they're not currently glass-backed).
  - No `Input`/`Select`/`Textarea`/`Label` React components exist yet in this worktree; the native-element tag-selector rule covers the actual rendered HTML either way, so the first story that creates those components should still reuse `glass-panel`/`glass-chrome` (never `--muted-foreground` near them) rather than reinvent the look.
