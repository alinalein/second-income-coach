## Intent

**Problem:** During a turn the chat shows nothing until the final reply lands, so a longer turn feels frozen; and replies render as a single text blob with no headings/lists/bold, so longer answers are hard to scan. Today's three message kinds (`'message'`/`'notice'`/`'error'`) also render at two different font sizes (`text-sm` bubbles vs. the `Badge`'s own `text-xs`), which the chat font-size AC now forbids.

**Approach:** Add a turn-scoped SSE channel (AD-19 amended) carrying discrete progress-status events sourced from real `beforeModel`/`wrapModelCall`/`afterModel`/(future)`wrapToolCall` boundaries via a fixed step-to-label registry (AD-31); render the agent's final, already-moderated answer through `react-markdown` in its default configuration (AD-32); and unify all chat text onto one shared font-size value in `ChatMessage`.

## Boundaries & Constraints

**Always:** every progress label the client shows maps 1:1 to a backend-emitted step key via the registry; an unmapped step/tool falls back to one fixed generic key, never a blank state or the raw hook/tool name; the final answer is written to the SSE stream only after `afterModel` moderation has resolved (AD-11) — AD-12's guilt-language check does not bind any capability in this epic, so it's out of scope here, not silently skipped; the typing-effect reveal runs client-side over the complete, already-fetched text, with zero additional network activity; every new progress/status string ships with both an `en` and `de` key (AD-24) in the same commit that introduces it; `ChatMessage` keeps one `text-sm` constant applied to bubbles, the notice/error `Badge`, and every Markdown element override — headings/bold differ only by `font-*`/spacing classes.

**Never:** no `dangerouslySetInnerHTML`, no raw-HTML-passthrough Markdown plugin (`react/no-danger` must still pass); no new tool in this story — `wrapToolCall`'s progress hook is wired now (so later tool-introducing stories only add a registry entry + i18n key) but is unreachable until a tool exists; GET `/api/chat/messages` (history) stays plain JSON, not SSE; no change to `src/agent/language.ts`, `src/agent/moderation.ts`'s existing exports, or `src/tools/**`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Happy turn | user sends a normal message | SSE: `progress checking_message` → `progress generating_response` → `progress checking_answer` → `result` (kind `'message'`), then client-side typing reveal | N/A |
| Jailbreak-rejected turn | message flagged `jailbreaking` at `beforeModel` | SSE: `progress checking_message` → `result` (kind `'notice'`) — no `generating_response`/`checking_answer`, since the model is never called | N/A |
| Unsafe output replaced | `afterModel` flags the reply | full progress sequence, then `result` carries the fixed fallback text (unchanged AC2 behavior from Story 1.4) | N/A |
| Model call exhausts retries | model throws after `setNodeDefaults` retries | `progress checking_message` → `progress generating_response` → stream ends with `result` (kind `'error'`, fixed EN/DE fallback, same `detectReplyLanguage` pick as today) | caught in the route handler, written as the terminal event, stream still ends cleanly (no crash) |
| Unmapped tool step (forward-looking; no tool exists yet) | `wrapToolCall` fires with a name absent from the registry | resolves to the fixed `tool_fallback` step key, never the raw tool name | N/A |
| Markdown reply with a `<script>`/`<img onerror>` payload | model output contains raw HTML-looking text | renders as inert escaped text via `react-markdown`'s default (no raw-HTML plugin), never executes | N/A |

- `src/api/routes/chat.ts` -- `POST /messages`: after schema validation, write SSE headers (`Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`), call `agent.stream({ messages: [userMessage] }, { configurable: { thread_id: threadId }, streamMode: ['custom', 'values'] })`. The returned iterator yields `[mode, payload]` tuples (verified directly: `streamMode` as an array makes every chunk a two-element tuple, confirmed via a throwaway script against the real compiled graph -- `['values', {messages:[...]}]` once per superstep, `['custom', {type:'progress', step}]` once per progress event). After the iterator completes, run that last `'values'` payload's last message through the existing `toChatMessage` to build the terminal `event: result` frame, then `res.end()` -- **not** a separate `agent.getState(...)` call (Design Notes: "getState() race"). Guard every `res.write`/`res.end` call: skip if `res.writableEnded`, and don't let a write failure (client disconnected mid-turn) throw past the handler. Catch block writes the existing fixed EN/DE fallback as the `result` event instead of a JSON body. `GET /messages` is unchanged (still uses `agent.getState(...)` -- that read has no concurrent-write race to avoid, since it's not paired with a same-request write).
- `web/package.json` -- add `react-markdown` (`^10.1.0`).
- `web/src/chat/sse.ts` (new) -- `parseSseStream(response): AsyncGenerator<{event: string; data: string}>`, reads `response.body`, buffers partial chunks, splits on blank-line-delimited frames. After the read loop ends (`done`), call `decoder.decode()` once more with no arguments to flush any pending partial multi-byte UTF-8 sequence into the buffer before parsing the trailing frame -- without this, a reply ending mid-character at a chunk boundary silently drops those bytes.

- `web/src/chat/progressLabelScheduler.ts` (new) -- `createProgressLabelScheduler(onChange, minDisplayMs = MIN_LABEL_MS)`; see Design Notes / Spec Change Log for the min-display-time behavior.
- `web/src/chat/ChatMessage.tsx` -- one `const CHAT_TEXT_CLASS = 'text-sm'` applied to the bubble (every kind, including notices/errors -- review follow-up: no separate `Badge`/pill, the `Badge` import is removed) and every Markdown `components` override; `animate?: boolean` prop -- when true and `kind === 'message'`, reveals `content` through the same `react-markdown` render as the complete text (see Design Notes: typing reveal). `message.kind` maps to the bubble's `role` (`'alert'` for `error`, `'status'` for `notice`, no role for `message`) -- the only remaining distinction, never a different visual treatment. Only render through `react-markdown` for `message.role === 'assistant'` -- AC7 scopes Markdown rendering to "an agent response containing Markdown"; a user-typed message (`role === 'user'`) renders as plain text so literal `**`/`#` characters a user types are never reinterpreted as formatting in their own bubble.
- `web/src/locales/{en,de}/chat.json` -- add a `progress` namespace: `checking_message`, `generating_response`, `checking_answer`, `tool_fallback` (EN wording taken directly from the AC's own examples).

## Implementation Notes

- **`resultEventSchema`'s `message` field uses `z.lazy(() => chatMessageSchema)`, not a direct reference:** `shared/schemas/index.ts` re-exports `progress.ts` via `export * from './progress.js'`, and `progress.ts` imports `chatMessageSchema` back from `index.ts` — an ESM import cycle. ESM evaluates a module's dependencies to completion before the importing module's own top-level code runs, so regardless of where the `export *` line sits in `index.ts`, `progress.ts` was evaluating `z.object({ message: chatMessageSchema })` before `index.ts` had reached its own `chatMessageSchema` declaration, silently binding `message` to `undefined` and failing every `resultEventSchema.parse(...)` call at runtime with "expected a Zod schema" (caught by `chat.test.ts`'s SSE-encoding tests, not by typecheck). `z.lazy` defers the reference to first-parse time, after both modules have finished loading, with no change to the schema's external shape or inferred type.
- **`wrapToolCall`'s `toolName` is coerced via `String(...)`:** `request.tool` is typed `ClientTool | ServerTool | undefined`, and `ServerTool` is `Record<string, unknown>` — `.name` isn't statically a `string` on that branch. `String(request.tool?.name ?? request.toolCall.name)` satisfies the compiler and is defensively correct; unreachable in this story regardless (no tool exists yet).
- **`src/agent/index.test.ts` and `src/api/routes/chat.test.ts` needed substantive rewrites, not just additions:** Story 1.3/1.4's `chat.test.ts` fakes drove `agent.invoke`/asserted a JSON body; the route now calls `agent.stream(...)` + `agent.getState(...)` and returns SSE frames, so the existing fakes and assertions were updated in place (same I/O-matrix rows/ACs they already mapped to, not new coverage) rather than left broken or duplicated alongside a parallel new set.
- No new external service/credential introduced by this story (`react-markdown` is a build-time npm dependency, not an external service) — no `.env.example` or `src/config/env.ts` changes needed, and there is nothing for the user to fill in.

## Design Notes

- **Progress middleware ordering:** registered *before* the moderation middleware in `createCoachAgent`'s `middleware` array so its `beforeModel` hook is never skipped by moderation's own `jumpTo: 'end'` short-circuit on a jailbreak reject — this is what makes the "jailbreak turn shows `checking_message` then jumps straight to the rejection notice, no fake `generating_response`/`checking_answer`" row in the I/O matrix correct rather than accidental.
- **`wrapToolCall` wired now with an empty registry:** AD-31's "each tool-introducing story registers its own label key, same pattern as the env-variable rule" implies the *hook plumbing* is this story's job; later stories add one `TOOL_STEP_REGISTRY` entry + one i18n key, not new middleware wiring.
- **Why `.stream()` + a hand-written SSE writer, not LangGraph's built-in `encoding: 'text/event-stream'`:** that built-in mode emits a versioned protocol envelope (`method`/`params`/`seq`) designed for LangGraph Platform parity, not a hand-rolled Express route; forwarding raw `'custom'`-mode chunks through our own two-event (`progress`/`result`) wire format stays simpler, matches the existing `chatMessageSchema` the frontend already parses, and avoids coupling to an internal protocol shape.
- **Why `streamMode: ['custom', 'values']`, not `'custom'` + a separate `agent.getState(...)` read (review loop 1):** a separate `getState()` call after the stream ends reads the *thread's* current state, not *this invocation's* own result — a second concurrent request against the same `thread_id` (two tabs of the same signed-in user, or an overlapping resubmit) could complete its own turn first and have its reply read back by the other request's `getState()` call. Requesting `'values'` alongside `'custom'` on the *same* `.stream()` call instead yields that invocation's own state after each superstep, scoped to only this call — confirmed directly against the real compiled graph: with `streamMode: ['custom', 'values']`, chunks arrive as `['values', {messages}]` once per superstep and `['custom', {type:'progress', step}]` once per progress event; the last `'values'` chunk's `messages` is this invocation's own final result, with no cross-request read. `GET /messages` keeps using `getState()` — a plain read with nothing racing a same-request write.
- **Guarding `res.write`/`res.end` against a mid-turn client disconnect:** the SSE loop holds the response open for the whole turn (seconds, not the near-instant single write the old JSON response made) — long enough for a tab close or navigation to land mid-turn. Writing to an already-ended/destroyed response doesn't necessarily throw into a surrounding `try/catch` (Node may instead emit an unhandled `'error'` on the response); every `res.write`/`res.end` call checks `res.writableEnded` first and is itself guarded so a post-disconnect write failure can't escape the route handler.
- **Typing reveal renders through `react-markdown` throughout, hiding only a trailing incomplete marker (post-launch follow-up, superseding the original plain-text-then-swap design):** the growing prefix is fed into the same `<ReactMarkdown>` element as the complete text, with `hideIncompleteMarkdownTail` trimming a trailing unclosed `**`/`*`, bare heading `#`, or bare ordered-list `1.` back to the last safe point first — since the reveal is always a strictly growing prefix of the final, well-formed text, an unclosed marker found at the very end can only be the one currently being typed. Hides the whole still-ambiguous span (marker plus whatever follows it, e.g. a bold word mid-typing) rather than showing its inner text unstyled and re-rendering it once closed — simpler, and the hidden span is only ever one ~20ms tick wide. Reveal rate: `Math.max(1, Math.ceil(codePoints.length / 60))` code points per 20ms tick (~1.2s cap regardless of reply length) — a reasonable default, not a tuned UX value, same disclaimer style as `resilience.ts`'s retry/timeout constants.
- **Only the just-arrived message animates:** `ChatThread` tracks ids delivered via the SSE `result` event (not history `GET`) and passes `animate` only for those — history reads never re-trigger the reveal.
- **Progress label minimum display time (post-launch follow-up):** `progressLabelScheduler.ts` decouples the raw step sequence a turn emits from what's displayed, so a fast real sequence (most steps besides the actual model call are near-instant) can't flicker a label for a fraction of a second. Each label stays up at least `MIN_LABEL_MS` (1000ms, one shared constant); a step arriving sooner becomes the *pending* one, overwriting any earlier pending step, and is shown once the minimum elapses — so the display never lags real progress by more than one label. `clear()` (the final answer) always takes effect immediately regardless of how long the current label has been up — the answer is never delayed to satisfy the minimum. Client-side display timing only; `src/agent/progress.ts` still emits exactly the same real step events, and `sse.ts`'s frame parsing is untouched.
