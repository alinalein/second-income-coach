## Intent

**Problem:** Intake submit, idea generation, and plan creation are deterministic button clicks, but all three route through the full agent loop (model decides → tool → model narrates), adding needless round-trip overhead; intake additionally shows an alarming "this can take up to half a minute" hint, and `generate_ideas`'s server-authored trigger text gets moderated for no reason.

**Approach:** The three routes call the exact handler functions the agent's tools already wrap (`handleGenerateIdeas`, `handleCreatePlan`, and a new `classifyFailurePattern` for intake) directly, with no `agent.invoke` around them. Intake stores immediately and classifies `failurePattern` with one direct structured-output call on a fast, never-user-selectable internal model, run in parallel with one Mistral moderation call on the user's own free text. `chat.ts`/`plan-chat.ts` and `createCoachAgent`'s tool registration are untouched — free-form chat keeps the full loop and can still call these same tools.

## Boundaries & Constraints

**Always:**
- Call the same exported `handleGenerateIdeas`/`handleCreatePlan` functions the current tool wrappers call, with the same `Deps`/`Config`/`Args` shapes — their internal retry/timeout/transaction/Zod-validation logic is untouched.
- Moderate both intake free-text fields (`skillsInterests`, `stoppedBeforeText`) in one Mistral call via the existing `evaluateUserMessage`/`defaultClassify` (`moderation.ts`, reused as-is), run concurrently (`Promise.all`) with the one `classifyFailurePattern` call — classification is never sequenced after moderation.
- `POST /api/intake` only resolves once both calls finish, so idea generation (client-triggered right after "saved") can never start before classification is persisted.
- Keep the existing "unchanged `stoppedBeforeText` → reuse stored `failurePattern`, no classify, no re-moderate" fast path exactly as-is.
- PII flagged → redact (`redactPii`, applied independently to each stored field) and continue saving. Jailbreak flagged → reject with the same generic `502 {error:'Intake could not be saved'}` the old "tool never called" path already returns — no new message text.
- `agent/index.ts`'s tool registration stays untouched; `chat.ts`/`plan-chat.ts` keep the full agent loop (Story 6.2 evals unaffected).
- `INTAKE_CLASSIFIER_MODEL_ID` reuses the existing `TRANSLATION_MODEL_ID` registry entry (category `'translation'`, already excluded from `listSelectableModels`) — no new model id, no new env var, no migration.

**Never:**
- Never touch idea-card layout, plan workspace UI, Story 2.7 translation code, or anything in 2.9/3.2/3.3.
- Never weaken an existing retry, timeout, or validation rule inside `handleGenerateIdeas`/`handleCreatePlan`/the intake write path. (Round 2, user-directed, see Spec Change Log: the batch size is no longer fixed at `5` — `IDEAS_PER_BATCH` — and one new fail-fast validation path was added for "every search this round failed"; neither weakens an existing rule.)
- Never let a client-triggered idea generation start before the intake save response returns.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Valid first submit | New/changed `stoppedBeforeText` | classify + moderate run in parallel; row upserted with classified `failurePattern`; 200 "saved" | N/A |
| Unchanged `stoppedBeforeText` | Existing row, same text | Fast path: no classify, no moderate call; row upserted reusing stored `failurePattern`; 200 | N/A |
| Jailbreak-flagged free text | Either free-text field flags `jailbreaking` | No row written/changed | 502 `{error:'Intake could not be saved'}` (existing generic collapse) |
| PII-flagged free text | Flags `pii`, not `jailbreaking` | Redacted fields stored (per-field `redactPii`); save continues | 200, redacted text persisted |
| Generate ideas / create plan, direct call | Valid trigger | `handleGenerateIdeas`/`handleCreatePlan` called directly with the same args/config shape the tool wrapper used | Same 502 vocabulary on failure, unchanged |
| (Round 2) Idea generation, configured batch size | `IDEAS_PER_BATCH` = N (1-5) | Exactly N ideas persisted, schema/prompt/UI all reflect N, not a fixed 5 | N/A |
| (Round 2) Every search in the first round fails | All attempted `web_search` calls in one round error | No retry, no repair pass, no draft persisted, existing `suggested` ideas rows completely unchanged | 503 `{error:'search_unavailable'}`; client shows a distinct "search service unavailable" message, never the generic one |

New test in `PlanWorkspace.test.tsx` renders under `<StrictMode>` and asserts exactly one `POST /select/` call.
  2. **Server (any concurrent-request source, not just StrictMode — two tabs, a retry, etc.):** even with the client fixed, `plans.ts`'s `existingPlan` check has a race window; the existing `isUniqueViolationError` recovery only protects the DB *row* (confirmed: this is what let the live run still 200 twice), never the model call's cost — a second genuinely concurrent request still ran its own `handleCreatePlan`. Added an in-process `Map<ideaId, Promise<PlanResponse>>`: a second concurrent request for the same idea now awaits the first's in-flight creation and skips the welcome-message seed (which the first request's own flow already does once — doing it twice would double the fixed welcome message in the thread, since `AIMessage`s with no explicit `id` append rather than dedupe). New test asserts `createDraft` is called exactly once for two concurrent selects (stable across 5 repeated runs, same `Promise.all` race-harness precedent as the existing unique-violation test).

## Design Notes

- **Why classification sees the pre-redaction text when PII is flagged:** it runs concurrently with moderation (AC2's parallelism requirement), so sequencing redaction first isn't possible without serializing the two calls again; a `failurePattern` enum choice isn't sensitive output, and the stored/displayed text is still the redacted version either way.
- **Why both free-text fields get one combined moderation call, not just `stoppedBeforeText`:** the old agent-loop flow already moderated both together as a single message; narrowing to `stoppedBeforeText` only would drop coverage of `skillsInterests`, which this story's own "every piece of user-written text is still moderated" forbids.
- **Why `ideasAgent`/`plansAgent` stay constructed in `api/index.ts` unchanged:** both remain needed for `.getState`/`.updateState` (the plan welcome-message seed, both routes' `detectUserReplyLanguage`), which read/write the shared checkpointer's thread-keyed state regardless of which compiled instance is used; only `.invoke()` stops being called on them.
